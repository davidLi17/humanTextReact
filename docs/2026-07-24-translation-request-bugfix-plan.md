# 翻译请求 Bug 修复计划

## 问题

现有两条翻译路径可能出现请求已经发出、界面却没有有效内容：

- 选中文字后，后台和 Content Script 会分别发起一次翻译。两个请求共用同一个
  标签页请求槽，后启动的请求可能中止前一个请求。
- Popup 更新使用异步回调，但调用方在回调执行前就检查 Popup 是否关闭，检测逻辑
  实际无效。
- SSE 解析只接受 `data: `，并且只有 `delta.content` 存在时才读取推理内容，
  因此部分合法响应会被忽略。

## 修改

1. 后台右键菜单处理器成为选中文字翻译的唯一请求发起方，Content Script 只负责
   创建页面弹窗。
2. 显示新的页面翻译弹窗前，先取消该标签页的旧请求。
3. 标签页消息和 Popup 消息改为可等待的发送方式，并返回接收端是否可用。
4. SSE 解析兼容 `data:` 后有无空格的格式，独立读取正文和推理，并处理流末尾
   没有换行符的剩余数据。
5. 流正常结束但没有译文时显示明确错误，不再呈现空白成功状态。
6. 用户可见的翻译错误统一由翻译服务发送，外层调用方不再重复发送。

## 边界

- 不修改扩展消息名称、设置结构、历史记录或 API 配置。
- 不增加依赖，本次不实施 Request ID 协议。
- 保持 Popup 草稿、重试、停止和历史复用行为不变。

## 验证

- 运行 `bun run compile`。
- 运行 `bun run build`。
- 确认 Popup 能显示流式译文或明确错误。
- 确认快捷键和右键翻译每次只发起一个 API 请求。
- 确认新的选中文字翻译会停止该标签页的旧请求。
- 确认关闭 Popup 后不会留下失控的后台请求。
